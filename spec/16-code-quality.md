# 16 — Code Quality Standard

This standard applies to **every** change in this repo: Rust, SQL, TypeScript, scripts and tests, whether a human or a coding agent wrote it. It holds even when a task file doesn't cite it.

**How it's enforced.** Each rule is marked with one of two tags:
- **[tool]** means CI checks it mechanically, and a red build blocks the merge (§10 maps each rule to its tool).
- **[review]** means the reviewer checks it, using the checklist in §9.

**Conflicts.** If this standard conflicts with a task file, the task is wrong. A coding agent marks the task `blocked` and asks (AGENTS.md §0). It doesn't pick one side.

**Exceptions.** Exceptions are allowed only through the process in §11. An exception without a written reason is a defect.

## 1. Principles

- **CQ-01. Correct, then clear, then fast.** Optimise only with a measurement in the PR description.
- **CQ-02. Consistency beats preference.** Follow the surrounding code and this document, even when you'd do it differently. Propose style changes as a PR to this file, never inside a feature PR.
- **CQ-03. Make illegal states unrepresentable.** Prefer types, enums and DB constraints over runtime checks and comments.
- **CQ-04. Small, single-purpose changes.** One task means one concern (§8). Refactors go in their own PR, separate from behaviour changes.
- **CQ-05. Delete, don't disable.** No commented-out code, dead code, unused feature flags or "just in case" parameters. Git remembers.

## 2. Universal rules (all languages)

**CQ-10. Naming** [review]
- Identifiers are in English and use the glossary terms from `00-index.md` §3: `enrollment`, `payer`, `resource`, `session`, `hold`. Don't invent synonyms like `booking` for `reservation` or `student_course` for `enrollment`.
- No abbreviations except: `id`, `db`, `tx`, `ctx`, `http`, `api`, `url`, `dto`, `ics`, `pii`, `tz`, `i18n`, `bps`.
- Booleans read as predicates: `is_active`, `has_data`, `can_cancel`.
- Functions are verbs: `issue_invoice`, `resolve_tenant`.
- Units go in the name when the type doesn't carry them: `timeout_ms`, `radius_m`, `buffer_minutes`. Money is always `Money`, never a bare integer named `amount`.

**CQ-11. Size and shape limits**

| Unit | Limit | Enforcement |
|---|---|---|
| Rust function body | ≤ 80 lines | [tool] `clippy::too_many_lines` |
| Rust function arguments | ≤ 7 | [tool] `clippy::too_many_arguments`. Use a params struct instead |
| React component file | ≤ 200 lines | [review] |
| Any source file | ≤ 600 lines | [review]. Split by responsibility, not alphabetically |
| Nesting depth | ≤ 3 levels of blocks inside a function | [review]. Use early return, `let … else` and guard clauses |
| Cognitive complexity (TS) | ≤ 15 per function | [tool] Biome `noExcessiveCognitiveComplexity` |

Generated files are exempt. Large `match` tables over a closed enum may exceed the limits through §11.

**CQ-12. Comments** [review]
- Comments explain **why**: an invariant, a spec rule, a trade-off, or a non-obvious bug workaround with a link. Never narrate what the next line does.
- Public items carry doc comments that cite their spec IDs: `/// SCH-03: …`.
- `TODO` is allowed only as `// TODO(T-xxx): …` or `// TODO(#issue): …`, pointing at a real task or issue. A bare `TODO`, `FIXME`, `XXX` or `HACK` fails review.

**CQ-13. Literals** [tool + review]
- Business values never appear as literals (POL-02, TST-14).
- Technical constants are named `const` items with a `// technical:` comment that says why the value is what it is.
- Strings shown to users never appear in code. They go through i18n (§5).

**CQ-14. Text files** [tool] (`.editorconfig`)
- UTF-8, LF line endings, a final newline, and no trailing whitespace (except in Markdown hard breaks).
- Indentation: 4 spaces for Rust; 2 spaces for TS, JSON, YAML, TOML, SQL, CSS and Markdown; tabs only in the `Makefile`.

**CQ-15. Generated files** [tool]
- These are generated and never edited by hand:
  - `web/openapi.json`
  - `web/src/api/schema.d.ts`
  - `web/src/routeTree.gen.ts`
  - `.sqlx/`
  - `web/src/policy-schemas/`
  - `tasks/INDEX.md`
- They are committed, and they're regenerated by the command named in AGENTS.md §3.
- CI fails on drift (TST-10).

## 2A. Clean code practices (all languages) [review]

Architecture-level rules (layers, modules, ports) are in `17-clean-architecture.md`. These rules are about the code inside a function or type.

**CQ-16. Functions**
- **Do one thing at one level of abstraction.** A function either orchestrates (calls other functions) or computes (does the detail). It doesn't do both.
- **Command–query separation.** A function either returns information or changes state. Domain aggregate methods are the exception: they change state *and* return the resulting facts (CA-23).
- **No boolean flag arguments.** `issue(invoice, true)` hides meaning. Use two functions or an enum: `issue(invoice, Delivery::Silent)`.
- **Few arguments.** Aim for ≤ 4. At 5–7, group them into a params struct; above 7 is a lint error (CQ-11).
- **Pure where possible.** Pass in what a function needs (`now`, `policy`, `facts`) instead of reaching out for it.
- **Guard clauses over nesting.** Validate and return early (`let … else`, `?`), so the main path reads straight down.

```rust
// ✗ Flag argument, nesting, hidden clock, mixed abstraction levels
fn process(inv: &mut Invoice, send: bool) {
    if inv.status == Status::Open {
        if Utc::now().date_naive() > inv.due_on {
            inv.total += 100_000; // late fee?
            if send { mailer::send(&inv.payer_email, "late") }
        }
    }
}

// ✓ One decision, explicit inputs, named concepts; sending is someone else's job (an event)
fn late_fee(terms: &LateFeeTerms, invoice: &InvoiceFacts, today: NaiveDate) -> Option<Money> {
    if invoice.status != InvoiceStatus::Open {
        return None;
    }
    let overdue_days = (today - invoice.due_on).num_days();
    (overdue_days >= i64::from(terms.apply_after_days)).then(|| terms.amount_for(invoice.outstanding))
}
```

**CQ-17. Names reveal intent**
- Name things after what they mean in the school, not how they're stored: `outstanding`, `makeup_credits_left`, `slot_is_free`. Not `amt2`, `data`, `info`, `tmp`, `result`, `obj`, `item`, `manager` or `handler2`.
- A name's length matches its scope. `i` is fine in a three-line loop. A module-level item gets a full name.
- If a name needs a comment to explain it, rename it. If you can't name a function without "and", split it.

**CQ-18. Data and mutation**
- **Immutable by default.** Use `let`, not `let mut`, and `const`, not `let`, in TS. Prefer returning new values over mutating arguments. In React, never mutate state or props.
- **Tell, don't ask.** Don't pull fields out to make a decision about an object (`if inv.status == Open && inv.paid < inv.total`). Ask the object (`inv.is_payable()`).
- **No primitive obsession.** Use newtypes and enums (CQ-23) instead of `String`/`i64`/`bool` for ids, money, statuses and units.
- **Total over partial.** Prefer functions that handle every input, either by returning `Option`/`Result` or by using the type system to rule out bad input. Don't use functions that panic or return sentinels like `-1` or `""`.

**CQ-19. Duplication and abstraction**
- **Rule of three.** Duplicate once if you must. On the third copy, extract the shared code.
- Only extract things that change for the *same reason*. Two pieces of code that merely look alike but belong to different concepts stay separate. The wrong abstraction costs more than duplication.
- **YAGNI.** No parameters, generics, traits or config "for the future". Build what the task's Scope → In needs (CA-10).
- **Boy-scout rule, within scope.** Leave touched code a little cleaner (a rename, an extracted function). Anything bigger goes in a separate `refactor:` PR (CQ-04).

## 3. Rust

**CQ-20. Toolchain and formatting** [tool]
- Use the pinned stable toolchain (`rust-toolchain.toml`) and edition 2024.
- `rustfmt.toml` uses **stable options only**: `max_width = 110`, `use_field_init_shorthand = true`, `use_try_shorthand = true`. Never use nightly rustfmt.
- Import grouping [review]: one block each for `std`, external crates, workspace crates (`eq_*`) and `crate::`/`super::`, separated by blank lines. Prefer one `use` per crate, with nested braces. rustfmt keeps the order inside each block stable.

**CQ-21. Lints.** These are workspace-wide, inherited by every crate through `[lints] workspace = true`. CI runs clippy with `-D warnings`, so `warn` is effectively `deny` in CI.

```toml
[workspace.lints.rust]
unsafe_code = "forbid"
missing_debug_implementations = "warn"
unused_qualifications = "warn"

[workspace.lints.clippy]
# correctness and robustness
unwrap_used = "deny"
expect_used = "warn"
panic = "warn"
todo = "deny"
unimplemented = "deny"
dbg_macro = "deny"
print_stdout = "warn"
print_stderr = "warn"
# numeric safety (money, durations, ids)
cast_possible_truncation = "warn"
cast_possible_wrap = "warn"
cast_sign_loss = "warn"
cast_lossless = "warn"
# exceptions must be explicit and justified (CQ-110)
allow_attributes = "deny"
allow_attributes_without_reason = "deny"
# shape (CQ-11)
too_many_lines = "warn"
# readability
semicolon_if_nothing_returned = "warn"
redundant_else = "warn"
manual_let_else = "warn"
explicit_iter_loop = "warn"
```

`clippy.toml`:

```toml
too-many-lines-threshold = 80
too-many-arguments-threshold = 7
allow-unwrap-in-tests = true
allow-expect-in-tests = true
allow-panic-in-tests = true
allow-print-in-tests = true
disallowed-methods = [
  { path = "chrono::Utc::now", reason = "use the injected eq_core::clock::Clock (ARC-10)" },
  { path = "chrono::Local::now", reason = "use Clock + the tenant timezone" },
  { path = "std::time::SystemTime::now", reason = "use Clock" },
  { path = "std::env::var", reason = "read config only through eq_core::config (OPS-01)" },
  { path = "std::thread::sleep", reason = "blocks the runtime; use tokio::time::sleep" },
]
```

- `eq-billing` also denies `clippy::float_arithmetic` with `#![deny(clippy::float_arithmetic)]` in its `lib.rs` (ARC-11).
- The single legitimate caller of each disallowed method (for example `SystemClock::now`, and `eq_core::config` reading env vars) uses a §11 `#[expect(…, reason = "…")]`.
- If a derive or proc macro (e.g. `sqlx`, `utoipa`) trips `allow_attributes` in generated code, don't add an exception. Block the task and ask, because the fix belongs in the lint config.
- `expect()` and `panic!` are allowed only during startup in `eq-server/src/main.rs`, and only with an `#[expect]` reason. Never in a request path.

**CQ-22. Errors** [review]
- Each library crate has one `thiserror` error enum per module boundary, named `<Area>Error`. It converts into `eq_core::error::AppError` at the service/HTTP edge (ARC-12, API-04).
- Use `anyhow` only in `eq-server` (main, CLI) and inside job runners.
- Error messages are lowercase, with no trailing period, and **contain no PII**. Add context, not noise. Right: `"invoice {id} is already paid"`. Wrong: `"Error: Something went wrong!"`.
- Never discard errors with `let _ = …`, `.ok()` or `unwrap_or_default()` unless the value is truly optional. In that case a comment says why.
- Match on error variants exhaustively. No catch-all `_ =>` arms on our own enums, so that new variants cause compile errors.

**CQ-23. Types** [review]
- IDs are newtypes (`PersonId(Uuid)`, `InvoiceId(Uuid)`), so a `PersonId` can't be passed where an `InvoiceId` is expected.
- Use `Money` and `Bps` for money and percentages. Durations use `chrono::Duration` or a named `*_minutes: u16` field. Never a bare `i64`.
- State is an `enum`, never a set of booleans (`status: InvoiceStatus`, not `is_paid` + `is_void`). Transitions are methods that return `Result` (DOM state machines).
- Constructors validate. If a value can be invalid, expose `TryFrom`/`new() -> Result` and keep the fields private.
- Visibility: default to private. Use `pub(crate)` for crate internals. Use `pub` only for what other crates use. Module re-exports live in `lib.rs`.

**CQ-24. Layering** [tool + review]
- Follow 02 §3 strictly:
  - `domain/` is pure. No `sqlx`, `axum`, `tracing` subscriber setup, clock, env or IO (ARC-03).
  - SQL lives only in `repo.rs`.
  - Transactions are opened only in `service.rs`.
  - HTTP types (extractors, DTOs, status codes) live only in `http.rs`.
- Cross-module rules are ARC-02, checked by `check-deps.sh`.
- DTOs (`http.rs`) are separate types from domain types, even when they look identical today. Convert with `From`/`TryFrom`.

**CQ-25. Async** [review]
- Never block the runtime. Argon2, image processing, PDF/zip generation and large JSON go through `tokio::task::spawn_blocking`.
- Never hold a lock across `.await`. Clippy `await_holding_lock` is on by default; keep it on.
- Every outbound network call (SMTP, WhatsApp, webhooks, payment gateways) has an explicit timeout, from config or a `// technical:` const.
- Spawned tasks are tracked: a `JoinSet` or the job runner. No fire-and-forget `tokio::spawn` in request handlers.

**CQ-26. Logging and tracing** [tool + review]
- Use `tracing` with structured fields: `info!(invoice_id = %id, "invoice issued")`. Never interpolate values into the message.
- Levels:
  - `error`: a human must act.
  - `warn`: degraded, but handled.
  - `info`: one line per business event or lifecycle step.
  - `debug`: developer detail.
  - `trace`: hot loops.
- No PII ever: names, emails, phones, addresses, tokens, request bodies (SEC, TST-16). Log ids only.
- Instrument service functions with `#[tracing::instrument(skip_all, fields(...))]`. `skip_all` is mandatory so arguments never leak.

**CQ-27. Dependencies** [tool + review]
- Declare every dependency once in `[workspace.dependencies]`. Crates reference it with `dep.workspace = true`. No versions in member crates, and no `*` or git dependencies.
- A new dependency must be justified in the PR: why it's needed, its weekly downloads or maintenance status, and its license.
- `cargo deny` (SEC-22) checks licenses and advisories.
- Prefer the standard library or an existing workspace crate over adding a new one.

**CQ-28. Docs** [review]
- Every crate has a `//!` header: its purpose and its spec section.
- Every public function and type has a `///` summary that cites the spec ID.
- Fallible public functions have an `# Errors` section listing the variants.
- Examples in doc comments must compile (doctests run in `cargo test`).

## 4. SQL and migrations

**CQ-40. Naming** [review]
- Tables are plural `snake_case` (`invoice_lines`). Columns are `snake_case`.
- Foreign keys are named `<entity>_id`. Booleans start with `is_` or `has_`. Timestamps are `*_at timestamptz`, and dates are `*_on date`.
- Constraint and index names:
  - `<table>_<cols>_key` for unique constraints;
  - `<table>_<cols>_idx` for indexes;
  - `<table>_<rule>_check` for checks;
  - `<table>_<rule>_excl` for exclusion constraints.

**CQ-41. Schema rules** [tool + review]
- Every tenant table follows ARC-06: `tenant_id`, RLS enabled and forced. TST-06 checks this automatically.
- Money is `bigint` in minor units plus `currency char(3)`. Never use `numeric` or floats for money.
- Times are `timestamptz`, and ranges are half-open `tstzrange` (`[)`).
- Use `CHECK` constraints for enums and value ranges, and a DB constraint for every invariant the DB can express (CQ-03).
- Index every foreign key used in a lookup or join.

**CQ-42. Queries** [tool + review]
- Use only `sqlx::query!` / `query_as!` (compile-checked, offline data committed). Never build SQL by string concatenation.
- List columns explicitly. No `SELECT *`.
- No N+1 queries: a list endpoint runs a constant number of queries regardless of page size.
- Use keyset pagination (API conventions) for lists that can grow.

**CQ-43. Migrations** [tool + review]
- File names are `NNNN_<module>_<desc>.sql` (ADR-0012). Migrations are forward-only.
- **A merged migration is never edited.** Fix it with a new migration.
- One concern per migration. Explain non-obvious constraints in a SQL comment that cites the spec ID.
- Destructive changes (drop or rename) go in two releases: first stop using the column, then drop it.

## 5. TypeScript and React

**CQ-60. Compiler** [tool]
`tsconfig.json` sets:
- `strict: true`
- `noUncheckedIndexedAccess: true`
- `noImplicitOverride: true`
- `noFallthroughCasesInSwitch: true`
- `verbatimModuleSyntax: true`
- `forceConsistentCasingInFileNames: true`

Path alias `@/` → `src/`. Use relative imports only within the same folder.

**CQ-61. Lint and format** [tool]
- Biome with the `recommended` rule set, plus these rules at `error` (rule group names may shift between Biome versions; use the equivalent):
  - `noExplicitAny`
  - `noNonNullAssertion`
  - `useExhaustiveDependencies`
  - `noUnusedImports`
  - `noUnusedVariables`
  - `useImportType`
  - `noConsole`, which allows `console.error` only in `lib/` error reporting
  - `noDefaultExport`, with an override allowing it in `*.config.ts`
  - `noBarrelFile`
  - `noExcessiveCognitiveComplexity` with a maximum of 15
- Formatter: 2 spaces, line width 100, double quotes, semicolons, trailing commas `all`.
- No `// @ts-ignore`. `// @ts-expect-error` is allowed only with a reason, and only for third-party type bugs, with a link to the upstream issue.

**CQ-62. Files and naming** [review]
- Components are in PascalCase files with a named export of the same name (`ScheduleGrid.tsx` → `export function ScheduleGrid`).
- Hooks are `useX` in `useX.ts`. Other modules are camelCase (`format.ts`).
- Tests sit next to the code: `X.test.tsx`.
- Props types are named `<Component>Props` and declared directly above the component.

**CQ-63. Components** [review]
- Function components only.
- One exported component per file. Small private sub-components in the same file are fine.
- Keep render logic declarative. Derive values, don't sync them: no `useEffect` that sets state from props or query data.
- Prop drilling deeper than 2 levels → use a context, a route loader, or composition.

**CQ-64. State and data** [tool + review]
- Server state lives **only** in TanStack Query, through the hooks in `modules/<id>/api.ts`.
  - No `fetch` or `openapi-fetch` calls anywhere else.
  - Never copy query data into `useState`.
- URL-worthy state (filters, tabs, dates, pagination) lives in typed search params (TanStack Router).
- Forms use react-hook-form + zod, or `PolicyForm` (FE-20).
- **Module boundaries mirror the backend:** `src/modules/<a>/**` must not import from `src/modules/<b>/**`. Shared code goes to `components/domain/` or `lib/`. [tool] `scripts/check-web-boundaries.sh`

**CQ-65. UI rules** [tool + review]
- Colours, spacing and radii come from semantic tokens only (DS-02). No hex, `rgb()` or Tailwind palette classes like `bg-blue-500`. Inline `style` is only for dynamic CSS variables.
- Every user-visible string comes from `t()`, including `aria-label`, `title` and `alt`. School vocabulary uses `t('term.*')`. `i18n:check` requires both `en` and `id`.
- Every async view handles **loading, empty and error** states, using the shared `EmptyState` / `ErrorState` components.
- Accessibility (WCAG 2.2 AA, TST-11):
  - semantic elements first (`button`, not a clickable `div`);
  - every input has a label;
  - focus is visible and keyboard order is logical;
  - touch targets are at least 44×44 px on mobile.
- Money and dates are formatted only through `lib/format.ts` (tenant locale and timezone). Never use `toLocaleString` ad hoc.

**CQ-66. Errors** [review]
- API errors arrive as typed problems (`lib/api.ts`). UI copy comes from `errors.<code>`.
- No empty `catch {}`. A caught error is either shown, rethrown or reported. Swallowing one needs a comment that says why.

## 6. Tests

**CQ-80. What to test** [tool + review]
- Every task's listed tests are written with the exact names given (AGENTS.md §1).
- Every bug fix adds a regression test that fails before the fix.
- Coverage gates are in TST-01: at least 90% of `domain/`. Never write tests only to hit coverage. Every assertion must check behaviour.

**CQ-81. How tests are written** [review]
- Rust test names are `snake_case` sentences describing the outcome: `late_fee_applies_day_after_due`, not `test_late_fee_1`.
- TS tests use `it("shows alternatives when the room is taken")`.
- Structure: arrange, act, assert. One behaviour per test, and helpers come from `eq-testkit` builders.
- **Deterministic:**
  - time comes from `TestClock`/`ManualClock`, and randomness uses fixed seeds;
  - no sleeps in tests: wait on a condition with a timeout, or time-travel with `run_due(now)`;
  - no real network, only the mock channels.
- Tests are independent, and order or parallel execution never changes the result.
- `insta` snapshots stay small and focused. Snapshot a summary, not a 500-line JSON. Snapshot changes are reviewed line by line.
- Web tests query the way users see the page: `getByRole` / `getByLabelText`. Don't use test ids unless nothing else works.
- `#[ignore]` and `it.skip` require a linked issue in the same line. Quarantined tests are tracked and fixed within one milestone.

## 7. API contracts

**CQ-90.** API rules live in `07-api-conventions.md`. The quality points reviewers check:
- every handler has `#[utoipa::path]` and a permission check;
- problem `code`s are stable `snake_case` and never renamed;
- JSON fields are `snake_case`;
- a breaking change to a response shape needs a new field or version, never a silent change;
- every new `code` gets `errors.<code>` in `en` and `id`.

## 8. Git, PRs and review

**CQ-100. Commits** [tool + review]
- Commits follow Conventional Commits: `<type>(<scope>): <imperative summary> [T-xxx]`.
  - Types: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`.
  - The scope is the crate or module id (`billing`, `web`, `workspace`).
- Every commit is signed off (DCO, `git commit -s`).
- The summary line is at most 72 characters. The body explains why when that isn't obvious.

**CQ-101. Pull requests** [tool + review]
- One task or one concern per PR, with at most about **400 changed lines**, excluding generated files, lockfiles and snapshots. Bigger work gets split into tasks first.
- The PR title uses the commit format, because we squash-merge. CI checks the title.
- The PR template checklist is complete, and CI is green before review is requested.
- No force-push after review starts. Add fixup commits; the squash cleans them up.

**CQ-102. Review** [review]
- Every PR needs at least one maintainer approval, and the author never approves their own. PRs from coding agents are always reviewed by a human (AGENTS.md §1.8).
- Review comments are prefixed:
  - **`blocking:`** must change;
  - **`should:`** fix it, or reply with a reason;
  - **`nit:`** optional;
  - **`question:`** needs an answer before approval.
- Reviewers use the checklist in §9. "LGTM" without having read the diff isn't a review.

## 9. Review checklist (copy into reviews when useful)

1. **Spec:** does the change do what the task and spec IDs say, and nothing beyond Scope → In?
2. **Business values:** are any literals ones that should be policy fields (POL-02)?
3. **Transactions:** is every state change in tx → domain → repo → audit → outbox → commit (ARC-04/05)?
4. **Tenancy and security:** RLS on new tables? Permission check in every handler? No PII in logs or errors? Parameterised SQL? For PRs with security triggers, also run the `18-security-by-design.md` §8 checklist (SBD-81).
5. **Types:** newtype ids, `Money`/`Bps`, enums for state, validated constructors?
6. **Errors:** no swallowed errors, no `unwrap` in request paths, stable problem codes?
7. **Layering:** `domain/` pure, SQL only in `repo.rs`, no cross-module imports (backend or web)?
8. **Tests:** listed tests present, deterministic, meaningful assertions, regression test for fixes?
9. **UI:** tokens only, i18n `en`+`id`, loading/empty/error states, keyboard and screen-reader friendly?
10. **Hygiene:** no dead code, no unjustified `#[expect]`, generated files regenerated, docs updated?

## 11. Exceptions

- **CQ-110.** A lint exception uses `#[expect(clippy::<lint>, reason = "<why, citing spec or issue>")]` on the **smallest** item possible.
  - `#[allow]` is forbidden by lint (`allow_attributes`).
  - `expect` fails the build once the exception is no longer needed, so stale exceptions can't pile up.
  - In TS, use `// biome-ignore lint/<group>/<rule>: <reason>` on the single line.
- **CQ-111.** A script allow-list entry (`check-literals.allow`) carries a justification comment on the same line.
- **CQ-112.** A crate-level or file-level exception, or a change to this standard, needs a PR to this file and a maintainer's approval. Never slip it into a feature PR.
